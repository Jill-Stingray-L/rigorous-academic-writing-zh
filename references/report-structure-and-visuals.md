# 报告结构与视觉语义

本参考用于理论研究报告、项目研究报告、技术分析报告、咨询研究报告及含重要图表的论文。通用证据和成果完整性规则见 [研究严谨性与证据](rigor-and-evidence.md)；本文件只规定报告结构和图形、表格的增量行为。

## 一、报告主线与章节接口

报告应形成可复述的论证主线，而不是材料目录：

`现实问题 → 研究问题 → 理论或方法 → 数据或材料 → 分析 → 结果 → 模型或方案 → 实施含义`

这不是固定目录。每章明确接收哪些前序结果、解决什么问题、形成什么对象、指标、模型或判断，以及下游在哪里使用。理论章节说明原理、构件、适用条件和本研究的使用策略；项目或分析章节把方法落实到实际材料；方案章节区分设计结果与已经运行的系统。

小标题准确命名实际内容。是否保留小节按其独立论证功能判断，不按标题字数、段落数量或是否含图表机械判断。

应用型报告还应检查：删除本节后，`研究问题 → 方法 → 项目结果 → 模型或方案 → 实施用途` 是否发生实质断裂。没有造成断裂的章节再判断是否重复、只有过程说明，或缺少实际输出。

## 二、应用型成果可迁移性

项目数据、案例和底稿既可以是研究对象，也可以是形成方法的经验基础。只有出现以下情形之一时，才启用可迁移性审计：项目目标明确要求形成方法、模型、框架、标准或治理方案；正文声称成果可推广或复用；报告承担后续工作指导作用。纯粹描述或解释当前项目的报告不因此被强制增加方法论。

区分个案结果与方法成果：个案结果说明“当前对象具有什么关系或问题”；方法成果说明面对同类新对象时，应识别什么、按什么步骤和规则处理、形成什么输出。前者可以构成完整的项目发现，但不能单独承担“形成可复用模型或方法”的主张。

### 方法论交付闭环

对声称可复用的应用型成果检查：

| 环节 | 应回答的问题 |
|---|---|
| 定义 | 解决什么问题，适用对象和边界是什么 |
| 构件 | 完整成果包含哪些元素，各自承担什么作用 |
| 建立步骤 | 输入、操作、判定规则和输出是什么 |
| 标准表达 | 是否有抽象模型、模板、结构表、关系图或其他稳定表达，使读者知道完整成果的形态 |
| 代表性实例 | 是否用实际材料展示如何落地；实例不得代替一般模型 |
| 迁移规则 | 更换对象、系统或场景时，哪些部分直接复用，哪些需要重新识别或配置 |
| 实施用途 | 如何转化为配置、治理规则、任务、责任或验收内容 |

闭环缺项时，先根据现有材料补足表达；材料不足则缩小成果名称或可迁移主张，不能虚构步骤、配置或运行效果。成果类型本身的最低构件仍按 [研究严谨性与证据](rigor-and-evidence.md) 判断，本文件不另建模型词典。

### 代表性案例与明细交付

案例数量由结构差异和示范价值决定，优先覆盖不同对象类型、关系结构、治理难点或模型应用方式。多个对象只有字段名称不同而方法结构相同时，`一个完整实例 + 其他对象的迁移说明` 可以替代机械重复；判断标准是读者能否据此处理未展开对象。

当报告承担查询、复核或后续实施任务时，正文解释研究逻辑、模型和代表性结果，附录、附件、配置模板或项目清单承载需要逐项使用的明细。没有此类交付要求时，不为形式完整强制生成附件。

## 三、正文、表格与图形的选择

- 正文适合少量数字、概念解释、条件、因果或逻辑说明。
- 表格适合多对象、多属性的精确比较、分类规则、指标定义、映射关系或需逐项查找的结果。
- 图形适合流程、层级、网络、时间、趋势、分布、空间关系和模型构件。

选择标准是表达是否增加理解和可核验性。把文字放进彩色框、把两三项结论制成表，或用正文逐项复述表格，都不产生独立信息价值。

## 四、图形抽象层级

先判断图承担的知识层级，再检查它与章节功能是否匹配：

| 层级 | 主要内容 | 判断要点 |
|---|---|---|
| 理论或概念图 | 一般性构件、机制、关系、理论框架 | 原则上脱离当前样本仍成立，项目数据若出现应服务于说明而非冒充一般原理 |
| 方法图 | 输入、操作、判断、输出 | 能说明研究如何实施，步骤和判定与正文方法一致 |
| 项目结果图 | 当前项目的对象、分类、数量、分布或模型族 | 对象、范围和数字能追溯到当前材料 |
| 案例模型图 | 一般模型在具体系统、表、字段、对象、事件或过程中的实例化 | 能区分通用构件与项目取值，并展示映射关系 |
| 实施或配置图 | 系统位置、责任、运行步骤、部署或治理关系 | 区分设计、计划、配置与已运行状态 |

层级是语义判断，不是形式分类。理论图可以出现数字，项目图也可以抽象；关键是数字、对象和关系在图中承担什么功能，以及图所在章节是否把理论、方法、项目结果、案例实例化和实施状态混为一层。理论图、项目结果图和案例模型图不能只是同一关系更换标题、数字或节点名称。

## 五、图表增量信息

每张图表相对于正文和其他图表都应增加至少一种新的结构、关系、结果、比较、尺度、层级或验证作用。审计时记录：

| 图表 | 独立问题 | 新增信息 | 与相邻正文或图表的差异 | 后续用途 | 处置 |
|---|---|---|---|---|---|

如果两张图只是同一流程换配色，或理论图与项目图只替换节点名称而分析功能不变，则合并、删除一张，或重新界定二者的知识层级和用途。贯穿案例的图可以跨章出现，但每次必须增加本章特有信息。

正文不逐项重复图表。图后文字优先回答：最重要的关系或差异是什么、据此得到什么判断、该判断如何进入后续分析。

## 六、视觉语义审计

处理 DOCX、PDF 等含图文档时，工具条件允许即渲染并查看相关页面或提取嵌入图。文本解析只能检查编号、题注和引用，不能替代以下语义核对：

- 图题是否准确概括图的实际内容；
- 图中层级、步骤或构件数量是否与正文定义一致；
- 节点、分组、变量和术语是否与正文稳定名称一致；
- 箭头方向、连接条件、线型和颜色是否有明确且合理的含义；
- 图例、单位、范围、来源和必要注释是否完整；
- 图中数字是否与正文、表格和统计口径一致；
- 是否残留临时文字、错字、占位符、制作提示或模型生成痕迹；
- 是否混淆理论、方法、实证和实施层级；
- 是否与其他图表实质重复，或图形复杂度掩盖了核心关系。

视觉问题由 LLM 结合页面和正文判断，不为节点数、标题长度、数字出现位置或其他形式设置机械阈值。Python 仍只负责可可靠定位的编号、重复编号、缺图和未引用等线索。

## 七、图表说明与排版

正文对每张重要图表交代其用途、读法、主要结果和所支持的判断；简单图表可以合并说明，复杂模型可以在图前后分别完成。只写“如图所示”或只重复图题不构成论证。

- 图题、表题和编号遵循目标模板；图内不无理由重复图题。
- 字体、线宽、箭头、颜色、间距、图例和分辨率在最终页面尺度下可读。
- 颜色之外使用必要的形状、线型或文字编码，保证灰度和色觉差异下可辨。
- 图表数字、术语、单位和正文一致；表格数值精度与对齐方式一致。
- 正式图注、表注和来源项按规范保留；待办、制作说明和占位文字不得进入成稿。
- 表格单元格不继承正文首行缩进，整段解释放回正文。

## 八、标题与章节接口审计

“标题像 AI”属于编辑反馈，不是作者身份判断。将其转化为可核对的问题：并列项是否承担不同功能，子标题相对父标题增加了什么，标题颗粒度是否与同级一致，以及“设计、计划、实施、运行、成效”等词是否符合材料支持的项目状态。

对目录或标题树建立最小工作表：

| 标题 | 层级功能 | 相对父级的新增信息 | 与同级的分类维度 | 证据或实施状态 | 处置 |
|---|---|---|---|---|---|

按以下顺序审计：

1. 先保护目标模板、专业术语、研究对象、范围、成果类型和计划或已实施状态。
2. 判断章节是在定义概念、说明方法、呈现项目结果、展开实例、规定规则，还是说明实施计划；同级标题应尽量采用同一分类维度。
3. 检查子标题相对父标题是否增加独立对象、关系、结果或用途。父标题已承担的共同语境可上移，不重复完整句壳。
4. 结果型标题只有在正文证据支持时才写具体发现；材料不足时保持对象或任务型标题，不把计划改写成已经完成的成果。
5. 最后删除没有导航价值的泛词，保持目录、正文、图表题注和附录中的术语、编号与时态一致。

脚本可以定位多项并列、同级重复后缀、父子计划与完成状态混用、编号格式异常等候选，但不得据此自动改名。标题长度、名词密度、重复率和连接词数量没有跨文稿通用的合格阈值；不禁用顿号或“与”，不强制动词标题，也不为制造变化而轮换稳定术语。有意义的平行标题和专业限定应保留。

## 九、交付前检查

- 每个图表均有正文引用和独立论证用途；
- 图形层级与章节知识层级相符；
- 视觉内容、题注、正文和其他图表口径一致；
- 图表提供信息增量，正文没有逐项复述；
- 项目图中的对象和数字可追溯，实施图未把设计写成运行成效；
- 声称可复用的应用型成果已完成方法论交付闭环，代表性案例足以支持迁移而非机械穷举；
- 附件或底稿与正文成果边界清楚；
- 标题准确反映章节功能，父子层级有信息增量，计划与已实施状态符合证据；
- 已实际查看图形页面，而非只核对抽取文本；若工具条件不允许，明确记录该审计缺口。
